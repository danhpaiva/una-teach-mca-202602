## O que fazer
1. Leia primeiro os arquivos existentes (mkdocs.yml, docs/*, workflow) para
   entender a estrutura antes de mudar qualquer coisa.
2. A partir da EMENTA, monte um cronograma coerente de aulas (uma lista por
   aula), com numeração limpa e sequencial (sem duplicar números). Se a ementa
   não deixar claro o número de aulas, proponha uma quantidade e me pergunte
   antes de gerar tudo.
3. Antes de gerar o conteúdo, use perguntas objetivas para confirmar: linguagem
   dos exemplos, quantidade de aulas/listas e se devo reescrever o index.
4. Crie os arquivos:
   - `docs/index.md`: página inicial com objetivo da disciplina (baseado na
     ementa), cronograma em tabela (Aula | Assunto | Entrega), ferramentas e
     dicas de estudo. Use abas (`=== "..."`) e admonitions (`!!! info`, etc.).
   - `docs/aulas/NN-aula.md` (uma por aula): conteúdo didático e envolvente, com
     admonitions, abas para comparar conceitos, tabelas, diagramas Mermaid quando
     fizer sentido, exemplos de código na linguagem escolhida, e uma seção de
     exercícios em blocos recolhíveis (`??? abstract`). Terminar cada aula com um
     `!!! tip "Próxima Parada"` e um link para a lista correspondente.
   - `docs/listas/NN-lista.md` (uma por aula): no padrão "Missão", com passo a
     passo de entrega (criar repositório público «una-xxx»-listaNN, subir código,
     entregar link no Google Classroom), exercícios em `??? abstract`, estrutura
     de pastas sugerida e um checklist de qualidade (`!!! check`).
5. Atualize `mkdocs.yml`:
   - `site_name`, `site_url` e `site_author` corretos para esta disciplina.
   - `nav` com todas as aulas e listas.
   - IMPORTANTE: títulos de nav que contenham dois-pontos (`:`) DEVEM ficar entre
     aspas, senão o YAML quebra (ex: `- "07. Controle: IF-ELSE": aulas/07-aula.md`).
   - Habilite Mermaid (via `pymdownx.superfences` com custom_fence) e, se usar
     fórmulas, `pymdownx.arithmatex` + MathJax.
6. Remova arquivos-template órfãos que não forem usados (ex: aula de introdução
   genérica, pastas de rascunho vazias). Deixe o projeto/trabalho comentado no
   nav (vou defini-lo depois).
7. Garanta que o workflow `.github/workflows/ci.yml` use o padrão de DOIS jobs
   (build e deploy separados), pois isso evita o erro "Multiple artifacts named
   github-pages" ao re-executar o deploy. Se ainda estiver num job único, ajuste
   para:

   - job `build`: checkout (fetch-depth: 0) → setup-python → pip install -r
     requirements.txt → mkdocs build → actions/configure-pages@v5 →
     actions/upload-pages-artifact@v3 (path: ./site)
   - job `deploy` (needs: build): environment github-pages →
     actions/deploy-pages@v4
   - Adicione um grupo de `concurrency` (group: pages-${{ github.ref }},
     cancel-in-progress: true) e permissions: contents: read, pages: write,
     id-token: write.

8. Valide localmente com `python -m mkdocs build` e corrija quaisquer erros
   ANTES de commitar (avisos de "no git logs" e de páginas fora do nav como
   setup.md são inofensivos).
9. Só depois de o build passar, faça o commit (mensagens em Conventional Commits,
   em português) e o push para `main`. Acompanhe o run do GitHub Actions e me
   confirme quando o deploy concluir com sucesso, informando a URL do site.

Se precisar de mais informações, me pergunte.
